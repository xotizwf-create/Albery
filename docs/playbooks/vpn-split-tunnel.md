# Раздельный VPN-туннель: через VPN только то, что напрямую не работает

## Зачем

До 16.08.2026 через туннель до Эстонии шёл **весь** внешний трафик коробки: в таблице 200
стоял `default dev awg0`, а исключений было четыре (DNS провайдера, локальная сеть, endpoint
пира). В тот день туннель час держал рукопожатия и терял ~90% данных — и вместе с ним
отвалились Битрикс, Google, Zoom и GitHub, хотя ни одному из них VPN не нужен: Битрикс
напрямую отвечает за 1,15 с. Один сбой инфраструктуры выключил продукт целиком.

Новая модель: **в туннель уходит только allowlist, всё остальное идёт напрямую.** Простой
VPN теперь выключает ровно те сервисы, которые за ним живут (мозг агента), и не трогает
портал, почту, диск и деплой. Побочный выигрыш: тревога о мёртвом VPN уходит в Битрикс
напрямую — то есть доходит именно тогда, когда она нужна.

## Состав

| Файл в репозитории | Куда ставится | Что делает |
|---|---|---|
| `deploy/vpn-apply.sh` | `/usr/local/sbin/vpn-apply.sh` | строит правила и таблицу 200 (по умолчанию — напрямую) |
| `deploy/vpn-split-routes.sh` | `/usr/local/sbin/vpn-split-routes.sh` | резолвит allowlist и держит его маршруты через `awg0` |
| `deploy/vpn-split-domains.conf` | `/etc/albery/vpn-split-domains.conf` | сам allowlist |
| `deploy/vpn-split-routes.service/.timer` | `/etc/systemd/system/` | пересборка allowlist раз в 3 минуты |
| `deploy/vpn-watchdog.sh` | `/usr/local/sbin/vpn-watchdog.sh` | проверяет связность КАЖДЫЙ прогон, ограничивает перезапуски, зовёт человека |
| `deploy/vpn-healthcheck.sh` | `/usr/local/sbin/vpn-healthcheck.sh` | ручная диагностика |
| `scripts/vpn_direct_probe.sh` | запускается из репозитория | замер: что реально работает напрямую |

## Порядок применения

### 1. Замерить, а не угадать

```bash
cd /var/www/albery && ./scripts/vpn_direct_probe.sh
```

Смотреть надо на колонку **ВЕРДИКТ**, а не на голый HTTP-код. Убирать из allowlist можно
**только** то, у чего вердикт `напрямую`; `ГЕОБЛОК`, `нет связи` и `неясно` остаются в туннеле.

| Вердикт | Что значит | Что делать |
|---|---|---|
| `напрямую` | сервис ответил и обслуживает | из allowlist можно убрать |
| `ГЕОБЛОК` | HTTP есть, но обслуживать отказались по географии | оставить в туннеле |
| `нет связи` | соединение не состоялось (`000`) | оставить в туннеле |
| `неясно` | 403 с обеих сторон, оба сигнала промолчали | оставить в туннеле |

Вердикт `неясно` трактуется в безопасную сторону намеренно: цена ошибок несимметрична. Лишняя запись
в allowlist стоит немного трафика, лишнее удаление выключает мозг агента. Так 16.08.2026
повёл себя `auth.openai.com` — 403 и напрямую, и через туннель.

**Достижимость ≠ пригодность.** 16.08.2026 замер на проде показал у `api.openai.com`
совершенно живой HTTP 403 с телом `unsupported_country_region_territory`, а у `api.groq.com` —
403 `Forbidden`. Прежняя редакция этого плейбука гласила «любой HTTP-код означает, что туннель
не нужен» — и по ней следовало вынести из туннеля мозг агента и голосовые, то есть выключить
их. Замер теперь различает три исхода: `напрямую`, `ГЕОБЛОК`, `нет связи`; поведение закреплено
тестом `tests/unit/test_vpn_direct_probe.py`.

Ошибка в сторону «добавить лишнее» возвращает нас к старой модели; ошибка в другую сторону
молча убивает Telegram-агента или голосовые, поэтому шаг обязателен.

### 2. Заполнить allowlist по результатам замера

`/etc/albery/vpn-split-domains.conf`. Широкие CDN-диапазоны запрещены: вместе с нужным
сервисом в туннель уедет половина интернета (тест `test_shipped_config_routes_openai_and_nothing_broad`).

### 3. Применить с автоматическим откатом

Правка маршрутов — единственное изменение, которое может отрезать саму возможность его
починить. Поэтому сначала ставится отложенный откат, и только потом применяется новое:

```bash
# Снимок текущего состояния — на него и откатимся.
ip rule show > /root/vpn-rollback.rules
ip route show table 200 > /root/vpn-rollback.table200

# Автооткат через 10 минут, если его не отменить.
systemd-run --on-active=10min --unit=vpn-rollback \
  /bin/bash -c 'ip route flush table 200; while read -r l; do
      ip route add table 200 ${l#default}; done < /root/vpn-rollback.table200'

/usr/local/sbin/vpn-apply.sh          # новая политика
/usr/local/sbin/vpn-healthcheck.sh    # проверка
```

Если после применения сайт и SSH живы, а `vpn-healthcheck.sh` даёт `RESULT: OK` —
отменить откат:

```bash
systemctl stop vpn-rollback.timer 2>/dev/null; systemctl reset-failed vpn-rollback 2>/dev/null
```

Не успели проверить — откат сработает сам, и коробка вернётся в прежнее состояние.

### 4. Проверить по реальному отказу

Главная проверка не «туннель поднялся», а «продукт переживает падение туннеля»:

```bash
ip link set awg0 down
curl -s -o /dev/null -w 'bitrix=%{http_code}\n' https://b24-0xrp3s.bitrix24.ru/   # ожидаем 302
curl -s -o /dev/null -w 'openai=%{http_code}\n' https://api.openai.com/v1/models  # ожидаем 000
ip link set awg0 up && /usr/local/sbin/vpn-apply.sh
```

Битрикс обязан отвечать при выключенном туннеле — ради этого всё и делалось.

## Грабли

- **Правила 900/901/902 обязательны.** Они возвращают ответы сервера (исходящий порт 22/443/80)
  в основную таблицу. Без них ответ на входящее соединение уходит в туннель, обратный путь
  рвётся, и коробка пропадает из сети целиком — сайт, API и SSH разом. Вотчдог их проверяет.
- **Маршруты `dev awg0` исчезают вместе с интерфейсом.** После каждого перезапуска туннеля
  allowlist надо пересобрать — этим занимаются таймер и вотчдог.
- **Молчащий резолвер — не повод удалять маршруты.** Старые адреса сохраняются (состояние
  хранится с владельцем записи), иначе моргнувший DNS отрезает агента от его же мозга.
- **Свежее рукопожатие ≠ рабочий туннель.** Проверять `awg show awg0 transfer`: принято ≈0
  при живых рукопожатиях означает, что данные теряются по дороге.
- **Перезапуск лечит не всё.** Если причина снаружи, вотчдог после нескольких попыток
  перестаёт дёргать туннель и шлёт тревогу владельцу.
